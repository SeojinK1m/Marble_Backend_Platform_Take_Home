     Marble Backend Take-Home — Implementation Plan

     Context

     Build the Marble backend/platform take-home (see CANDIDATE_BRIEF.md): a
     small backend over a restaurant dataset (12 CSVs in data/, 100k-sale
     fixture in scale_data/) that supports idempotent revision-aware imports,
     site-scoped read APIs with source citations, one human-approved order
     workflow against the local fake supplier (simulator.py, port 8765), and a
     measured cheap-correction demo at scale. Timebox: 4–6 hours total including
     docs. Decided: Python 3.10+, FastAPI, stdlib sqlite3 (no ORM), SQLite WAL.
     Balanced effort across all four requirements.

     Deps: fastapi, uvicorn, httpx, pytest. DBs are gitignored: app_small.sqlite
     (from data/) and app_scale.sqlite (from scale_data/) — never merged,
     selected via --db / MARBLE_DB.

     Numeric policy: store all source columns as TEXT verbatim; all arithmetic
     at the read boundary uses decimal.Decimal; money returned as strings. One
     cast exception: SUM(CAST(quantity_sold AS INTEGER)) for the scale
     aggregate.

     Repo layout

     app/
       db.py          # connect(): WAL, synchronous=NORMAL, busy_timeout=5000;
     init_schema()
       registry.py    # TABLES = {name: {natural_key, columns}} for all 12 CSVs
     — drives DDL + importer
       importer.py    # upsert_record(), import_csv_dir(), apply_update_file(),
     ImportStats
       auth.py        # Bearer token -> caller(site_id) dependency;
     seed_callers()
       queries.py     # purchases(), usage(), counts() with citations + gaps
       orders.py      # order state machine + persistence
       supplier.py    # httpx client for the fake supplier (Bearer
     demo-supplier)
       main.py        # FastAPI app, routes, error mapping
       cli.py         # init-db | import-csv DIR | apply-update FILE |
     seed-callers  (--db PATH)
     scripts/bench.py   # scale measurements
     scripts/demo.sh    # curl walkthrough incl. supplier-timeout recovery
     tests/             # conftest +
     test_importer/test_queries/test_auth/test_orders
     ARCHITECTURE.md  RUNBOOK.md  NOTES.md  requirements.txt  transcripts/

     git init at the repo root (packet .gitignore already exists); commit at
     each phase boundary.

     Schema (key points)

     - Current-state table per CSV (generated from registry.py), PK (site_id, 
     natural_id), plus lineage columns: source_revision INTEGER, content_hash
     (sha256 over non-revision fields), source_file, imported_at.
     - Natural keys: sites→site_id, invoice_headers→invoice_id,
     invoice_lines→row_id, vendors→vendor_id, vendor_catalog→catalog_row_id,
     ingredient_mappings→mapping_id, menu→pos_item_id, recipes→row_id,
     pos_daily→row_id, inventory_counts→row_id, notes→note_id,
     supplier_documents→document_id.
     - row_versions (table_name, site_id, natural_id, source_revision, payload
     JSON, source_file, superseded_at): superseded versions for "what changed".
     - import_conflicts: equal-revision/different-hash records, kept, never
     applied.
     - callers (token, caller_name, site_id): seed token-site-01→SITE-01,
     token-site-02→SITE-02.
     - orders (order_id, site_id, vendor_id, status, client_reference UNIQUE,
     content_hash, approved_hash/by/at, supplier_order_id, supplier_status,
     last_error, timestamps) + order_lines.
     - Indexes (the "measured improvement"): pos_daily(site_id, pos_item_id, 
     business_date), invoice_lines(site_id, sku), recipes(site_id, pos_item_id),
     inventory_counts(site_id, ingredient_name), ingredient_mappings(site_id, 
     sku) + (site_id, ingredient_id).

     Importer — one upsert path for CSVs and JSON updates

     upsert_record(conn, table, record, source_file) -> inserted | replaced | 
     noop_same | noop_stale | conflict:
     - no existing row → INSERT
     - rev > current → copy old row to row_versions, UPDATE → replaced
     - rev == current, same hash → noop_same (double-apply no-op)
     - rev == current, different hash → record in import_conflicts, keep current
     → conflict
     - rev < current → noop_stale (re-importing CSVs can't reverse a correction)

     import_csv_dir: one transaction per file; bulk executemany fast path when
     the table is empty (keeps 100k-row first import fast), row-by-row upsert
     otherwise. apply_update_file parses {"table","record"} (format of
     updates/pack_correction.json) into the same path.

     API (Bearer auth except /health; wrong-site access → 404, bad token → 401)

     - GET /health
     - GET /sites/{site}/ingredients/{ing}/purchases?start=&end= — invoice lines
     via ingredient_mappings; qty = quantity × pack_quantity as captured on the
     line (never current catalog); spend = Σ line_total; grouped by unit, no
     invented conversions
     - GET /sites/{site}/ingredients/{ing}/usage?start=&end= — pos_daily ×
     recipes, recipe row = max effective_from <= business_date, usage =
     quantity_sold × quantity/yield_portions (Decimal); items sold with no
     recipe → gaps (unknown, not zero)
     - GET /sites/{site}/ingredients/{ing}/counts — raw observations, no derived
     balance
     - POST /sites/{site}/orders (draft) · GET .../orders/{id} · POST 
     .../orders/{id}/approve (body {"content_hash"}, mismatch → 409) · POST 
     .../orders/{id}/submit · POST .../orders/{id}/reconcile

     All read responses: {answer, sources: [{file, site_id, row_id, 
     source_revision, ...}], gaps: [...]}.

     Order state machine

     DRAFT -approve(hash match)-> APPROVED -submit-> [persist SUBMIT_PENDING
     BEFORE HTTP]
       201/200 -> SUBMITTED   409 -> REJECTED   network error -> stays
     SUBMIT_PENDING
     SUBMIT_PENDING -retry submit-> same client_reference+payload (supplier
     idempotent, 200)
     SUBMIT_PENDING -reconcile-> GET ?client_reference: found -> SUBMITTED;
     empty -> APPROVED

     client_reference = "{site_id}-{order_id}" fixed at draft creation; lines
     immutable after approval (hash recheck on submit). State in the same SQLite
     file → survives restarts.

     Bench (scripts/bench.py, fresh bench DB, in-process calls)

     1. Full scale_data/ import: wall time, rows written, RSS
     2. Affected query (SITE-01 chicken purchases/usage) + unrelated control
     (another site) — values + latency, before
     3. Reader thread polls the affected query every ~10 ms while main thread
     applies updates/pack_correction.json → update time, write count (expect 1
     replaced + 1 row_versions), reader p50/max latency (WAL proof)
     4. Re-apply repeated_pack_correction.json → noop_same, 0 writes
     5. After: affected qty 80 lb → 40 lb, money unchanged; control
     byte-identical
     6. Clean rebuild into second DB, assert answers equal, report
     rebuild-vs-update time ratio
     7. Peak RSS via resource.getrusage (bytes on macOS, KB on Linux — print
     platform + unit); EXPLAIN QUERY PLAN for the indexed usage query as the
     explained improvement

     Tests (11, supplier stubbed via monkeypatched app.supplier)

     1. re-import data/ twice → all noop_same
     2. pack correction → replaced, old row in row_versions
     3. correction then CSV re-import → still corrected (noop_stale)
     4. equal-rev different content → conflict recorded, row unchanged
     5. repeated update file → noop_same, zero writes
     6. purchases: 2×40 lb = "80" lb, spend "256.00", sources cited; after
     correction "40" lb, spend unchanged
     7. usage respects effective_from; missing recipe → gap not zero
     8. counts verbatim with citations
     9. auth: own site 200, other site 404, no token 401
     10. order happy path + wrong-hash 409 + idempotent resubmit
     11. ConnectError on submit → SUBMIT_PENDING survives → reconcile →
     SUBMITTED

  What was built

  Stack: Python 3.14 / FastAPI / stdlib sqlite3 in WAL mode. Two gitignored
  databases — one for data/, one for scale_data/ — never merged, per the data
  guide.

  Importer (app/importer.py + python -m app.cli): one revision-aware upsert path
  shared by CSV imports and JSON correction files. Higher revision replaces
  (old row audited into row_versions), repeat applies are no-ops, stale
  re-imports can't reverse a correction, and equal-revision-different-content is
  recorded in import_conflicts rather than silently applied.

  Read APIs: purchases (billed qty × the pack size captured on that line —
  catalog changes never rewrite history), recipe-based usage (respects
  effective_from; an item with no recipe at all is an unknown gap, not zero),
  and raw count evidence. Every response carries sources (file, row id,
  revision) and gaps. Seeded bearer tokens scope callers to one site; cross-site
  access returns 404.

  Order workflow: draft → approve (caller must echo the exact content hash) →
  submit → outcome. SUBMIT_PENDING is persisted before the HTTP call, so when I
  armed the simulator's supplier-timeout scenario live, the dropped-after-accept
  connection left the order recoverable and reconcile resolved it to SUBMITTED
  with the supplier's order id. Resubmits are idempotent via the stable
  client_reference.
