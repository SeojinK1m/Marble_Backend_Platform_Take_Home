15	**Import and update records.** Store the supplied data in a way that supports repeated imports and later corrections. Keep enough source information to explain an answer and what changed. 16

1	# Fake supplier API
2	
3	Start: `python3 simulator.py serve --mode supplier` (Python 3.10+, standard library only).
4	Base URL: `http://127.0.0.1:8765`. Use `Authorization: Bearer demo-supplier`.
5	This simulator calls no external services. It is not an implementation of your backend. Its source is supplied so setup and failures are inspectable.
6	
7	`GET /health` needs no token. Errors are JSON `{"error":"code"}`. SITE-01 and SITE-02 are supported. The supplier token is a backend integration credential; do not give it to an untrusted caller. Your application owns caller authorization and human approval.
8	
9	## Submit an order
10	
11	`POST /supplier/orders` with JSON:
12	
13	```json
14	{"client_reference":"your-stable-reference","site_id":"SITE-01","vendor_id":"V1","lines":[{"sku":"AW-CHK20","quantity":2,"unit":"case"}]}
15	```
16	
17	Valid lines use catalog SKUs for the named vendor, integer quantities 1–100, and catalog order units. Use 1–20 distinct lines. The supplier does not model final prices, payments, or delivery.
18	
19	201 returns `order_id`, `client_reference`, `status: accepted`, and `order` with the submitted business fields. The reference belongs to this supplier account across sites. Submitting the same reference and payload returns 200 with the existing order. Reusing a reference with different contents returns 409. A new reference creates another order. Accepted means recorded by the supplier, not received by the restaurant.
20	
21	## Check an outcome
22	
23	`GET /supplier/orders?site_id=SITE-01&client_reference=your-stable-reference`
24	
25	Returns `{"orders":[...]}`. An empty array means no matching order exists. Omitting the reference lists that site's orders. The fixture keeps orders across process restarts. Your backend must keep its own state across restarts too.
26	
27	## Exercise a network failure
28	
29	With the server running, the human/developer runs:
30	
31	```sh
32	python3 simulator.py scenario --name supplier-timeout
33	```
34	
35	The next new order is saved, then its connection closes without a response. This models a request with an uncertain outcome; the client may see a connection error rather than a literal timeout. Reads continue working. `--name normal` clears the failure flag without deleting orders. Existing-order retries do not consume the flag; it affects the next new order only.
36	
37	For separate fresh runs, stop the server and use a new `--state path.sqlite`. Supply the same `--state` to scenario commands. All commands also support `--port`. The local operator helper is test control, not part of your application's public API.

## 1. Order state transitions have no compare-and-swap — concurrent requests can lose updates

**Scenario.** Every status change in `app/orders.py` is an unconditional `UPDATE orders SET status=? WHERE order_id=?`. The read-check-write sequence (`get_order` → validate status → `UPDATE`) is not atomic across the two per-request connections. Concretely: a retry `submit` and a `reconcile` run concurrently on a `SUBMIT_PENDING` order. Reconcile's GET to the supplier returns empty (the retry's POST hasn't landed yet), so reconcile writes `APPROVED`. The retry's POST then succeeds and writes `SUBMITTED`. Depending on interleaving, reconcile's write can land *after* and regress `SUBMITTED → APPROVED` — the order claims it was never sent while the supplier has an accepted order.

**Current handling.** Not handled. The system only converges by luck: because the payload is frozen and the `client_reference` is stable, a subsequent resubmit gets the supplier's 200-existing and repairs the status. But between the regression and that repair, the API reports false state, and nothing forces the repair to happen.

**Reproducible test.** Monkeypatch `supplier.submit_order` to block on a `threading.Event`, call `submit` in a thread, then run `reconcile` (with `lookup_orders` returning `[]`), then release the event. Assert final status — it will be whichever write landed last, and you can force the `APPROVED`-after-`SUBMITTED` ordering deterministically.

**Smallest fix.** Make every transition a CAS: `UPDATE orders SET status=? ... WHERE order_id=? AND status=?`, check `cursor.rowcount`, and raise a 409 `OrderError` on 0 rows. ~6 line changes across `approve`/`submit`/`reconcile`.

## 2. Reconcile's "no record → back to APPROVED" can contradict an in-flight submission

**Scenario.** Distinct from the race above, this one is sequential. A submit attempt fails with a connection error, but the request is merely *slow*, not dead — or the supplier persists it after our socket closed (exactly what the `supplier-timeout` scenario models). The late POST then lands: the supplier now holds an accepted order for a draft our system says was never submitted. If the human edits intent (abandons the order, or we ever add a cancel flow), the supplier has a ghost order that nothing reconciles, because `APPROVED` is not a state `reconcile` accepts.

**Current handling.** Partially. Resubmission is safe (same reference → supplier returns the existing order), so the happy path self-heals. The unhappy path — abandon after reconcile — leaves permanent divergence, silently.

**Reproducible test.** Monkeypatch `submit_order` to raise `ConnectError` but *also* record the order into the fake supplier's state after a delay (or: against the live simulator, arm `supplier-timeout`, submit, and call reconcile from a script racing the simulator's persist — the simulator persists first, so instead test the inverse claim: assert that after reconcile returns `APPROVED`, a supplier lookup by that reference is guaranteed empty forever. **Current handling.** Not handled; it works today because the test suite and demo are low-concurrency and anyio happened to reuse threads. This is the classic footgun the FastAPI docs' own SQLite example exists to prevent.

## 4. Proposed minimal correction

**Fix A — remove the illegal edge (V1).** Delete the `SUBMIT_PENDING → APPROVED` branch in `reconcile`. Empty lookup → stay `SUBMIT_PENDING`, return the order with a note in `last_error` ("supplier has no record yet; retry submit"). The only exits from `SUBMIT_PENDING` become retry-`submit` (safe: stable reference + frozen payload + supplier dedup) and reconcile-found. This is a net code *deletion*.

**Fix B — guard every transition with conditional updates (V2).** Each `UPDATE` gains `AND status = ?` (or `IN (...)` for T2) and checks `rowcount`. On `rowcount == 0` the actor lost the race: re-read and return the current state if it's already a legal outcome (e.g., someone else got it to `SUBMITTED` — idempotent success), else 409. Because SQLite serializes writers, the CAS makes each transition atomic without any explicit locking. Note that `SUBMITTED` must be *absorbing* under reconcile: reconcile-found may refresh `supplier_status` but its guard is `WHERE status IN ('SUBMIT_PENDING','SUBMITTED')` and the target is always `SUBMITTED` — monotone, so a stale reconcile can only re-affirm, never regress.

**V3 stays, documented.** Two concurrent submits can still both POST. I propose *not* adding an in-flight mutex: duplicate POSTs are explicitly safe under the supplier's idempotency contract, and both racers' outcome writes go through the same CAS (first wins, second re-reads and returns `SUBMITTED`). A mutex would add state for no additional guarantee.

**Guarantee attribution** (what we own vs. what we rely on):

- *Our database guarantees:* reference fixed at draft creation; payload frozen at approval and hash-verified at submit (I5); `SUBMIT_PENDING` durably persisted before any network I/O (crash recovery); CAS-serialized monotone transitions (I1, I3); all state survives restarts.
- *The supplier contract guarantees:* at most one order per `(account, client_reference)`, 200-existing on identical retry, 409 on payload mismatch. **I4 holds only as the conjunction of both.** If the supplier violated its dedup contract, we could create duplicates — unverifiable from our side, worth one line in ARCHITECTURE.md.

**Fix C — thread affinity:** `check_same_thread=False` in `db.connect` (one line). Safe because connections are request-scoped and never used by two threads simultaneously.

**Fix D — recipe temporal gap:** in `usage`, the no-candidates branch distinguishes three cases: no recipe at all (existing unknown-gap), recipe exists but none effective on the sale date (**new** "sold before recipe effective" gap bucket), recipe exists but omits this ingredient (known zero, unchanged). ~8 lines.

## The five decisions you're most likely to get grilled on

**1. SQLite with a CLI-only write path — "why not Postgres, and what breaks first?"**
Your defense: the write topology is one operator importing files; SQLite-WAL gives snapshot-isolated readers during writes (measured: p50 0.12 ms during a correction), zero setup for the demo, and the whole correctness story (CAS transitions, atomic directory import) is plain SQL that ports to Postgres unchanged. What to concede: it's single-writer — two concurrent *importers* would serialize on the write lock, and a multi-node deployment needs Postgres. Expect the follow-up "what exactly would you change?" — answer: connection handling and `busy_timeout` go away, the schema and upsert semantics move as-is, `WHERE status=?` CAS becomes `SELECT ... FOR UPDATE` or stays as-is since it's already optimistic.

**2. Storing every source value as verbatim TEXT, Decimal only at the read boundary — "you put *money* in a TEXT column?"**
Your defense: this is a system of *record* for someone else's exports — fidelity beats typing. Verbatim storage makes the content hash stable (which conflict detection and idempotency hang on), floats never touch money, and answers are deterministic. The one place it costs is SQL aggregation, paid exactly once with an explicit `CAST` on `quantity_sold`. Concede: no DB-level type checking, so a corrupt export lands in the table and surfaces at read time; validation-on-import would be the production hardening.

**3. Current-state tables + JSON audit, not full versioned storage — "how do you answer 'what did this look like last Tuesday?'"**
Your defense: the brief requires explaining *what changed* and that corrections beat rebuilds — `row_versions` delivers both for ~15 lines, and every read query stays a simple current-state query (no `WHERE valid_to IS NULL` tax on the 100k-row hot path). Concede honestly: there is no as-of time-travel query; reconstructing a past state means replaying the audit JSON. If they push "is that a real limitation?" — point out the exports themselves have no bitemporal semantics (a revision says nothing about *when* the truth changed, only that the record was corrected), so time-travel would be built on invented timestamps.

**4. The order workflow's handling of unknown outcomes — "why can't I cancel, and why does an empty supplier lookup not clear SUBMIT_PENDING?"**
This is the one they'll push hardest because the first version got it wrong and the transcript shows it. Own that: the original reconcile treated "supplier has no record" as proof of absence; the review showed a dropped-but-still-in-flight POST makes that unprovable, so the edge was deleted. Defend the shape: `SUBMIT_PENDING` persisted *before* the HTTP call, CAS-guarded monotone transitions (a `SUBMITTED` order cannot regress — tested with barrier-controlled interleavings), retry-submit as the safe exit. Know the attribution cold: *our* DB guarantees reference stability and payload freezing; the *supplier's* dedup contract guarantees at-most-one order — the invariant is the conjunction, and you can't verify their half. The residual they may find: an abandoned `SUBMIT_PENDING` can be a ghost accepted order at the supplier; no cancel flow exists because the supplier API has no cancel, so the honest answer is "reconcile-then-decide is the operator procedure."

**5. Query semantics: per-line pack capture, unknown-vs-zero, no unit conversion — "your purchases and usage are in *lb*; why can't I get one total number?"**
Your defense: three deliberate refusals to invent data. Pack quantity is read from the invoice line as captured, never from the current catalog — which is precisely what makes the pack correction change history correctly (the N11 ops-log note about 20 lb cases is the narrative for this). An item sold with no recipe (M99) or sold before its recipe's `effective_from` is reported as an *unknown* gap, not silent zero — while a recipe that merely omits the ingredient is a true zero; conflating those was a bug the review caught. And units group by source unit with no lb↔each conversion table because any factor would be an invented mapping. Concede: it pushes interpretation work to the caller; the counter is that the `gaps` array is the API contract for exactly that — the brief's "explain uncertain mappings rather than silently inventing them."
